# RAG 手写笔记：切分 → 向量化 → 检索 → 生成

> 对应代码 `rag.py`（全部手写，无第三方检索/切分库，零下载）。
> 一句话理解 RAG：**把外部文档切成小段存成向量，提问时先按相似度把最相关的段落捞出来，再连问题一起喂给 LLM 回答。** 让模型"开卷考试"而不是"闭卷背题"。

---

## 四步总览

```
   文档        切分           向量化          检索            生成
  data.txt ──→ chunk1      → [0.1,0.3,...] → 和问题向量   ──→ 拼进 prompt
               chunk2      → [0.8,0.2,...]   比相似度        "仅根据资料回答"
               chunk3      → [0.5,0.9,...]    取 top-3   ──→ DeepSeek 输出回答
               ...
```

| 步骤 | 对应函数 | 本质问题 |
|---|---|---|
| 1. 切分 | `chunk_text()` | 文档太长塞不下，切成多小的块？ |
| 2. 向量化 | `build_vocab()` + `tfidf_vectors()` | 文字怎么变成数字向量？ |
| 3. 检索 | `cosine_similarity()` + `retrieve()` | 怎么找出"和问题最像"的段落？ |
| 4. 生成 | `generate_answer()` | 怎么让 LLM 只根据捞出来的资料回答？ |

---

## 第 1 步：切分（Chunking）

**为什么**：LLM 上下文有长度限制（比如几万 token），整篇文档塞不进去；就算塞得进，问题相关的信息淹没在无关内容里，检索质量也差。所以要切成块，检索时只捞最相关的块。

**做法**（手写，不用切分库）：

```python
stride = chunk_size - overlap
start = 0
while start < n:
    end = min(start + chunk_size, n)
    chunk = text[start:end]        # 第 start..end 个字符
    start += stride                # 下一块从"前进 stride"处开始
```

字符位置示意（`chunk_size=60, overlap=20`）：

```
[0 ────────────── 60] chunk0
     [40 ───────────── 100] chunk1        ← 40 = 60 - 20
          [80 ───────────── 140] chunk2
         ↑↑ 区间 [40:60] 是重叠区，两个块都包含它
```

- 没重叠时：第二块从 60 开始 → 一个恰好跨越第 60 字符的句子会被拦腰切断。
- 有重叠时：第二块从 40 开始 → 跨越边界的句子完整保留在这一块里。
- **overlap 的意义：宁可让相邻块重复 20 个字符，也不让一句语义完整的话被切坏。**

> 升级到生产：真实项目一般按 **token 数** 切（而不是字符数），因为 LLM 按 token 计费/限量；更进阶有"语义切分"（按自然段落/句群，用 embedding 判断哪里断开）。但核心都是"定长 + 滑动窗口"这个思想。

---

## 第 2 步：向量化（手写 TF-IDF）

**为什么**：计算机只认数字。要把每段文字变成一个**定长向量**（一串数字），使得"语义相近的文字 → 向量也相近"。

**term（词元）怎么来**：不引 jieba，用「单字 + 相邻双字」：

```python
"退款到账" → 退/款/到/账/退款/款到/到账
```

双字能抓住"退款"这种有含义的词；`isalnum()` 顺手滤掉标点和换行。

**TF-IDF 权重**：

```
tf(词, 段)   = 词在段内出现次数 / 段的词总数      # 出现多 → 重要（归一化掉段落长短）
idf(词)      = log(N / (1 + 该词出现的段数)) + 1  # 到处都有 → 没区分度 → 压低
段向量[词]   = tf × idf
```

直觉：**"退款"在退款那段里出现、别处没有 → TF 高、IDF 高 → 权重很大**；**"的"在每段都出现 → IDF 接近 0 → 权重几乎为 0**，自动起到了"去停用词"的作用。

> 升级到生产：真实项目用的是**预训练 Embedding 模型**（如 OpenAI text-embedding、bge、m3e），一个词/句子直接映射成几百维向量，能理解"借钱"≈"资金周转"这种 TF-IDF 看不见的语义。TF-IDF 是"词面匹配"，Embedding 是"语义匹配"。

---

## 第 3 步：检索（手写余弦相似度）

**为什么**：问题也要变成一个向量，然后跟每一段的向量比"像不像"。

**余弦相似度**（全部手写，不调 numpy）：

```
cos(a,b) = (a·b) / (|a|·|b|) = Σ(aᵢbᵢ) / (√Σaᵢ² · √Σbᵢ²)
```

- **点积** `Σ(aᵢbᵢ)`：对应维度相乘求和，重合维度贡献大。
- **除以长度** `|a|·|b|`：消除向量长度差异，只比"方向"。长短不同的句子也能公平比较。
- 值域 `[-1, 1]`，越接近 1 越像。

```python
def cosine_similarity(a, b):
    denom = norm(a) * norm(b)
    if denom == 0:
        return 0.0
    return dot(a, b) / denom
```

`retrieve()` 把问题和每一段都算一遍 cos，按分数降序取 top-3。

> 升级到生产：真实项目用**向量数据库**（FAISS / Milvus / Chroma）做近似最近邻搜索（ANN），因为文档可能有百万段，逐个算余弦太慢。但"找最像的 k 个"这个目标不变。

---

## 第 4 步：生成（DeepSeek）

**为什么**：检索出的段落就是"开卷考试的参考书"。把它拼进 prompt，让 LLM 只根据这些资料回答，并明确"资料里没有就直说不知道"（防幻觉）。

```python
messages = [
    {"role": "system", "content": "只能根据提供的资料回答，没有的信息就直说不知道"},
    {"role": "user", "content": f"资料：\n{context}\n\n问题：{question}"},
]
```

**这一步才是 LLM 出场的地方** —— 前两步（切分/向量化/检索）在真实项目里通常可以离线跑、甚至没有 LLM 也能做。这也是"RAG"和"直接调 LLM"的本质区别：**知识不在模型参数里，而在每次检索出的文档里**，所以可以随时更新文档、不用重新训练模型。

## 实验：两种切分策略对比（真实运行结果）

同一问题「退款多久到账？」，`chunk_size=60`，`overlap` 分别取 0 和 20。答案句「审核通过后一般**三个工作日**左右原路退回您的支付账户」被刻意放在第 60 字符附近。

**策略 A：overlap=0（无重叠），切 5 块**

| 区间 | 相似度 | 内容关键点 |
|---|---|---|
| [0:60] | 0.2708 | 「…审核通过后一般三个」← **"工作日"被切没了** |
| [60:120] | 0.0526 | 「工作日左右原路退回您的支付账户。…」← 数字跑到下一块 |
| [120:180] | 0.0279 | 无关段落 |

→ 答案「三个工作日」被拆成两截，散落在两个块里。

**策略 B：overlap=20（有重叠），切 7 块**

| 区间 | 相似度 | 内容关键点 |
|---|---|---|
| [40:100] | **0.2917** | 「…审核通过后一般**三个工作日**左右原路退回您的支付账户」← **完整！** |
| [0:60] | 0.2729 | 「…一般三个」 |
| [120:180] | 0.0272 | 无关段落 |

→ 完整答案句落在 `[40:100]` 同一块里，且相似度最高。

**结论**：
1. 无重叠时，跨边界的句子被切坏，检索结果残缺；有重叠时，完整句子保住在同一块。
2. 同一个 chunk_size，**overlap 只增加少量冗余（20/60 ≈ 33%），换来的是检索上下文完整性的大幅提升**。
3. 注意重叠区 `[40:60]` 的两个块都包含它——检索时可能同时命中，属于正常现象，代价可接受。

> 实验里 chunk_size=60 是为了让效果肉眼可见；真实项目通常几百到上千字符/token。

## 这个 demo 的边界与生产差距（诚实说明）

| 环节 | 本 demo（教学版） | 生产（真实项目） |
|---|---|---|
| 切分 | 按字符数 | 按 token / 语义切分 |
| 向量化 | 手写 TF-IDF（词面匹配） | 预训练 Embedding 模型（语义匹配） |
| 存储 | Python 列表 | 向量数据库 + ANN 索引 |
| 检索 | 全量算余弦 | 近似最近邻（FAISS/Milvus）+ 可能加 rerank |
| 生成 | DeepSeek 单轮 | 通常加引用来源、流式输出 |

但**四步的骨架和每一步的"为什么"完全一致**——你手写的这段代码，就是把黑盒拆开后的真相。
